# RFC 0040 - Gating record accuracy and flaky tests

## Status

Discussion - opened 2026-08-31.

An RFC is a *request for comment*: it presents the options and a recommendation
so a decision can be made, and it is not itself the decision record. When it is
decided, set the status, then write the [ADR](../adrs/) that records the choice.

## Overview

**Decision to make.** Which gate changes do we adopt so that (a) an
intermittent test failure cannot reach `main` on a green run, and (b) a report
cannot claim `Status: Resolved` without machine-checkable evidence?

**Why now.** Both failed on 2026-08-31, in the same day, and each cost hours:

- A use-after-free in `net.transport` reached `main` and sat there through
  **several green gates**. Measured rate on the unmodified parent: **2 failures
  in 200** runs of the transport test binary. The gate runs each test step
  once, so a 1% defect passes 99% of the time. Recorded in
  `reports/bugs/2026-08-31-hub-listener-freed-under-accept.md`.
- An audit of 29 reports found **9 marked `Resolved` while the defect was still
  live**, and 20 correctly resolved but indistinguishable from them by any
  automated signal. See
  [research 0010](../research/0010-sweep-report-audit.md). Three agents spent a
  combined ~1.5M tokens re-deriving what a `Fix:` field could have asserted.

**Drivers.**

- Zig 0.16, std-lib only, no new external tool on the build path
  (see [RFC 0036](0036-ci-toolchain-pin.md)).
- The gate is already ~4 minutes; a change that multiplies that is not free,
  and a slow gate gets bypassed.
- No tracker exists and none is being adopted here
  ([RFC 0035](0035-record-store-tooling.md) owns that question).
- Whatever is added must fail *loudly and specifically*. The existing gate
  already emits stray `failed command:` lines in green runs, and a check whose
  output is ambiguous trains people to ignore it.

**Out of scope.** Adopting a bug tracker; changing the report template's prose
sections; CI provider choice; the `e2e` step's membership of the gate.

## Current state

`zig build test` runs 25 steps once each: the unit tests plus `zig build lint`
(fmt, 100-column cap, test registration and declaration analysis, gate coverage
completeness).

What is **not** gated today:

- **Nothing runs any test more than once.** A racy test is sampled once per
  gate.
- **No docs check runs at all.** `scripts/docs-index.sh --check` exists and
  works, but it is not wired into `build.zig` - `grep -nE 'docs-index' build.zig`
  returns nothing. The index is regenerated by convention only.
- **Nothing validates a report's `Status` against anything.** `Fix: none` sits
  under `Status: Resolved.` in 29 records with no complaint.
- **`build.zig` exposes no `--test-filter` pass-through**, so iterating on one
  test means either the full 4-minute gate or `zig test src/<file>.zig`
  directly. The latter works (imports are relative) and is what the audit used,
  but it is undocumented.

## Options considered

### A. Do nothing

Keep the gate as is; rely on reviewers and on repeated gate runs happening
naturally as PRs stack up.

- **For:** zero cost. The UAF *was* eventually caught this way.
- **Against:** it was caught by someone gating merged `main` out of caution,
  not by the gate. At 1% per run, a defect survives ~70 gate runs with even
  odds. The record problem does not self-correct at all - it compounds, because
  a wrong `Resolved` removes the item from anyone's view.

### B. Repeat the flake-prone steps inside the gate

Run the test steps N times (N≈20) and fail if any run fails.

- **For:** directly targets the sampling problem; no new tooling.
- **Against:** multiplies a 4-minute gate by N. At N=20 that is over an hour,
  which will be bypassed. Also mis-shaped: most steps are deterministic and
  gain nothing from repetition.

### C. A separate `zig build stress` step, repeating only the concurrency tests

A new step that runs the transport/cluster/sim test binaries M times with
random seeds. Not part of `zig build test`; run before a merge that touches
those files, and on a schedule.

- **For:** the cost lands only where races live. `zig test src/net/transport.zig`
  already runs in seconds, so M=200 is ~1 minute for the file that had the bug.
  Reproduces the measured 2/200 rate. Keeps the merge gate at 4 minutes.
- **Against:** it is opt-in, so it relies on judgement about when to run it -
  the same judgement that missed the UAF. Mitigable by naming the file set in
  `AGENTS.md` and by running it on a schedule, not by the gate.

### D. A `reports` gate check: `Resolved` requires a resolving reference

Extend the in-tree gate (alongside the existing marker scans) with a check
over `docs/reports/**/*.md`: if `## Status` begins `Resolved`, the References
section must carry a `Fix:` line naming a commit SHA or PR number, the SHA must
exist, and it must touch at least one file under `src/`. `Fix: none` under
`Resolved` fails the gate.

- **For:** it is exactly the assertion that was missing, it is cheap (a file
  walk plus `git cat-file -e`), it needs no new dependency, and it is
  retroactively satisfiable - all 29 records now carry the symbol they were
  verified against. It would have caught `8893ae1` at the moment it was
  authored, since that commit left `Fix: none` in place in all 29 files.
- **Against:** it cannot catch the two hardest cases found by the audit - a
  fix that is present but **unreachable** (`wire-read-drops-compacted-slots`),
  and a credited fix that is **wrong** (`sl.leader`). Both need a human reading
  a call path. So this raises the floor; it does not close the question.
  It also risks becoming a rubber stamp: pasting any plausible SHA satisfies it.

### E. Wire the existing docs-index check into the gate

One line in `build.zig` running `scripts/docs-index.sh --check`.

- **For:** trivial, and the check already exists and passes. Stops the index
  drifting silently.
- **Against:** narrow - the index was not the problem. Worth doing regardless.

### F. Out of the box: adopt a tracker and stop hand-maintaining statuses

Move status out of the markdown entirely.

- **For:** removes the whole class of defect.
- **Against:** [RFC 0035](0035-record-store-tooling.md) owns this and has not
  been decided; it is a much larger change than the failures here justify, and
  it does not help the flaky-test half at all.

## Recommendation

**Adopt C + D + E. Confidence 7/10.**

- **E** is unconditional: one line, the check exists and already passes.
- **D** is the highest value per unit of cost, because it makes the failure
  mode that actually happened - a docs-only commit flipping 29 statuses with
  `Fix: none` untouched - impossible to author. Its two known blind spots
  should be written into the report template's Verification section as
  questions a human must answer ("is the fixed path reachable from a caller?"),
  not pretended away by the check.
- **C** over **B** because gate latency is the thing most likely to get any of
  this bypassed, and the measured evidence (2/200 in ~1 minute of looping one
  file) shows the targeted version is sufficient to surface the defect.

Confidence is 7 rather than higher because **C is opt-in**, and the reason the
UAF survived was precisely that nobody opted into extra scrutiny. If a
scheduled run is not practical, C's value drops sharply and B at a small N
(3-5, applied only to the concurrency test steps) becomes the better trade.

Not recommended: **A** (the record problem compounds), **F** (out of proportion,
and owned elsewhere).

Also worth doing but not part of this decision: document
`zig test src/<file>.zig` for single-file iteration in `AGENTS.md`, and add a
`--test-filter` pass-through to `build.zig`. Both are developer velocity, not
correctness, and neither would have caught either failure.

## Open questions

- Where would a scheduled stress run execute? CI is currently unusable
  (see the `verify` failures noted in `reports/`), so "on a schedule" may have
  no host today. If it does not, C degrades to B.
- Should D also require the `Fix:` commit to be an ancestor of `main`? It
  would catch a SHA from an abandoned branch, at the cost of failing the gate
  on a PR that references its own not-yet-merged commit.
